01这是什么

CEVTUO-Z 把散在四个地方的个人数据 —— Notion 里的观影记录和笔记、 Kindle 上的阅读历史、手机里的健康数据 —— 收拢到一个站点上， 用同一套材质和同一套排版呈现。它既是给自己看的面板，也是一次 「同一份代码要同时活在浏览器和微信里」的完整工程练习。

一个来源

四扇门，一张皮

四个品牌共用一份设计 token、一份玻璃材质、一份导航实现。 改一处，全站跟着变 —— 不是四套各自为政的页面。

两端

网页与小程序同源

同一套 Taro + React 代码，编译成 H5 网页和 微信小程序两个产物，小程序里读的是同一个数据契约。

不设密码

数据是公开的

观影、笔记、阅读都可以随便看。只有健康数据是加密的 —— 因为那是唯一能指向一个具体身体的数据。

03技术链路

从一行代码到两个平台上跑起来的东西，中间经过这些环节。

框架

Taro 4.0.9 + React 18

一套 TypeScript 源码，两个编译目标： build:h5 出网页，build:weapp 出微信小程序。 组件、路由、样式都是 Taro 那一层统一掉的 —— 平台差异只写在少数几处。

单仓

bun workspaces

一个仓库里装着应用、数据契约、同步流水线和服务端： apps/dashboard、packages/schema、 pipeline、services/ingest。 它们共享同一份类型定义。

样式

SCSS token + 玻璃材质

所有颜色、圆角、模糊强度都是变量。卡片材质只有一处定义， 任何地方都不许自己写一份 —— 验收看的是计算值， 不是「我 include 了哪个 mixin」。

部署

一个源，三处出口

站点产物推到 gh-pages，GitHub Pages 与国内镜像都从它取。 数据由独立的发布桥写进同一个分支 —— 内容是天然同步的。

TypeScript 源码→ Taro 编译→ H5 产物↘ gh-pages→ GitHub Pages+ 国内镜像 :443
入口地址说明
主站z.cevtuo.com备案域名，443，深圳节点 —— 国内读者的主入口
备份z.cevtuogrnd.comGitHub Pages 直出，海外线路更快
应用页apps.cevtuogrnd.com本页所在的用户站，聚合各个项目

04数据链路

四条链路，每条都是「源头 → 采集 → 落到 gh-pages → 浏览器读」。 中间没有一台常开的个人电脑 —— 采集和发布都跑在云上或手机上。

01 · COOF 观影

Notion 观影库 → 网页

同步脚本按年历拉取 Notion 里的观影记录，配上豆瓣的海报图， 按年写成分片 JSON。海报走自己的 CDN，不写外链。

Notion 观影库→ Notion API→ 同步流水线→ data/coof/*.json→ gh-pages→ 浏览器
02 · CNSR 笔记

Notion 四个源 → 网页

四个数据库各自独立刷新（四个一循环），所以每个来源存成自己的文件 —— 合在一起的话，任何一个刷新都会让另外三个谎报新鲜度。

Shopping / Learn / tech-learn / TECH-AI→ Notion API→ data/cnsr/<源>.json→ gh-pages→ 浏览器
03 · CAPPERR 阅读

Kindle → 云 → 网页

Kindle 上的 KOReader 插件把阅读历史 POST 到云上的接入服务， 服务端用 GitHub API 直接写进 gh-pages。 这条链路里没有任何一台 Mac —— 机器是阿里云的一台小实例。

Kindle · KOReader 插件→ 接入服务 :8789→ GitHub API→ gh-pages→ 浏览器
04 · CHEALTH 健康

手机 → 云（加密）→ 网页

手机上装一个自己写的 App，定时把三星健康里同步过来的数据推到云上。 服务端按日期合并、只保留最近 31 天，再用 AES-GCM 密封才写进仓库 —— 因为仓库是公开的。浏览器里解开它只需要一个内置口令。

三星健康→ Health Sync→ Health Connect→ CEVTUO Health→ 接入服务 :8789→ AES-GCM 密封→ gh-pages→ 浏览器解密
桥 · 自动发布

数据落到线上的那一跳

同步跑完只把数据写进了仓库的主分支，而站点读的是 gh-pages。 这两者之间原先靠手工一条命令 —— 忘了跑，站点就停在某一天。 现在有一条自动桥：同步一结束就触发发布，另外每小时兜底一次。

定时同步→ main→ 发布桥→ gh-pages→ CDN→ 你看到的页面

05功能特色

这些是站上自己长出来的东西，不是买来的一套模板。

导航

Cnowbar —— 一条底栏取代整个顶栏

最左边是返回和一个 UO 圆盘，其余位置是这一页自己的分区： 点一下翻到那一屏，滚动的时候高亮也跟着走。 分区超过五个就折成一摞（后面露两层边），点它才摊开 —— 是折叠，不是隐藏，摊开那一下要有宽度动画。

UO

点 UO 展开「现在」

UO 展开后是最近 24 小时的成果流：看过什么电影、读过哪本书、 跑了多少、睡到几点 —— 一行一枚胶囊，右边挂一条卡尺刻度。 上下都能折叠，默认贴着「现在」。行按离视口中心的距离缩放淡出， 所以滚起来是波动的。设备状态（电量、网络）贴在右边。

字标

逐像素反色的名字

「CEVTUO Z」不是固定的黑或白 —— 它和身后的东西逐像素混色， 压在浅色上就变深、压在深色上就变亮，甚至同一个字母的各处都不一样。 所以它放在任何背景上都读得出来。

材质

玻璃，而且是同一块玻璃

全站的卡片用同一份材质定义：同一档模糊、同一档饱和度、同一圈高光。 验收的方式是量计算值在三页上是否真的相同 —— 不是看代码有没有引用。

画框

每页一张画，带画框

每个页面挂一张自己的画，永远在内容之下。窄屏允许被屏幕边裁掉， 但露出的面积一定大于一半。背景用的也是这些画。

翻页

一屏一屏地翻

每一页由几「屏」组成，滑动时整屏吸附过去。底部条的每个分区 就是其中的一屏 —— 两条路走的是同一套状态，不会互相打架。

双语

中文 / English

右上角一键切换，所有中文位置都换成英文 —— 包括圆盘里那个字

主题

深色 / 浅色

两种主题都是正式版，不是「深色加个滤镜」。凡随主题变的东西 （颜色、底色、阴影）两个主题各验一遍，判据是算出来的对比度。

08本地跑起来

开发与构建命令

需要一个 bun 环境。仓库是一个 workspaces 单仓。

# 开发（网页 / 小程序各一条）
bun run app:dev:h5
bun run app:dev:weapp

# 构建
bun run app:build:h5
bun run app:build:weapp

# 类型检查 —— 改过界面代码之后一定要跑
bun run typecheck

本地预览走 bash scripts/preview.sh： 它会类型检查、构建、重铺一份预览，并且起一个带 SPA 回落的本地服务器。

这个项目踩过的几个坑（写给下一个接手的人）

它们都在仓库的 docs/ 和交接文档里，简版：

同特异型的 CSS 谁赢只看导入顺序 写了不生效、且不报错。规则在别的文件里，看源码看不出来 —— 要去产物里数那个选择器有几条规则。
断言全绿 ≠ 断言在测东西 一组断言全盯着同一个对象时，另一个对象坏了没人管。加断言先问：它怎么才会红。
「量不到」会被读成「产品坏了」 工具链的毛病会伪装成被测对象的毛病。同一个检查器两次跑结果不同，先修抖动再谈结论。
随主题变的东西，两个主题都要看 只跑一个主题时，另一个主题下的问题可以活很久 —— 判据用算出来的对比度，不用「看起来还行」。
直连正常 ≠ 经代理正常 反向代理要把 Origin 转发过去，否则 CORS 头会静默消失 —— 而直连测永远看不出来。
